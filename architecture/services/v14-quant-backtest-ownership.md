# V1.4 daily backtest service ownership implementation note

Date: 2026-10-02. This is an implementation supplement to [Quant Research service design](./quant-research-service.md) and [Platform API service design](./platform-api-service.md); it records only the current V1.4 Fixture slice.

## Ownership and call path

Platform owns local user session checks, acceptance scenarios, TestRun identity, owner-scoped reads and the TestRun projection. It calls Quant Research through `GeneratedQuantV14BacktestClient`, generated from `packages/contracts/openapi/quant-v14-daily-backtest.v1.json`. The only allowed caller is the Platform API Bearer identity, scoped to `POST /v1/research/backtests/daily-fixture`.

Quant owns the computation path. `V14DailyBacktestService` depends on `V14DailyBacktestFixturePort`; bootstrap injects `V14DailyBacktestFixtureAdapter`, which reads the frozen CSV packaged in the Quant image and verifies SHA-256 `88a198cbf5e2cf8f3bf1351a31c5aba1b9d9c6ce2d28343fb05a1dc462569bef`. The domain engine receives validated daily bars and run-scoped execution policy. Quant's application layer creates the backtest result identity; Platform persists its own TestRun metadata and returned result projection.

The request schema permits only scenario, seed and bounded execution policy. Fixture rows and hashes are not accepted from Platform, so a caller cannot replace the fixed input while claiming the approved Fixture identity. The generated client checks the response UUID, V1.4 stage, scenario/seed binding, status and assertion/evidence shapes. Requests use a 16 KiB limit; unsupported fields or invalid policy are rejected.

For the current single-security daily Fixture, the Quant domain result includes `positionAvailability` by Fixture session. A close fill contributes to holdings and NAV on its execution date, but its quantity remains unsellable for that session; it becomes sellable on the next available Fixture session. An optional bounded SELL order uses explicit signal/execution dates and quantity; an attempted same-session sale is rejected as `T_PLUS_1_UNAVAILABLE`. A later sale is capped by holdings and daily volume participation, incurs adverse slippage and the configured fixed fee, and records unsettled proceeds on its execution date. Those proceeds enter settled cash on the next available Fixture session; when the Fixture ends first, they remain an unsettled receivable. The Web renders the order outcome, cash ledger and settlement, and the browser-created runs are checked by CLI against the same persisted TestRun.

## Verified behavior and remaining boundary

`pnpm test:integration:v14-backtest` builds a dedicated Compose project with random PostgreSQL storage and verifies normal, rejection and recovery runs, Platform persistence, browser-created TestRun plus same-run CLI check-only, and removal of only that project's containers, volume, network and images. The audit records the actual TestRun IDs and hashes.

Quant now persists BacktestRun and hash-bound Manifest in its own PostgreSQL transaction; Platform separately owns the user-facing TestRun and result projection. The current automated proof is bounded to the single-security close/volume Fixture and one optional SELL order. It verifies T+1 rejection, subsequent sellable quantity, volume-bounded fill, sale costs, and next-Fixture-session cash settlement. It does not establish exchange calendars beyond the Fixture sessions, suspensions, price limits, corporate actions, complete market/side fee and tax schedules, Qlib/Paper parity, real market data, complete manual acceptance, or Ubuntu readiness. Keep V1.4 PARTIALLY_IMPLEMENTED until the remaining required items are completed and accepted.
