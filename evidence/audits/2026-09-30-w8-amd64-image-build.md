## Database authentication release blocker

Review of the resolved Compose configuration found `POSTGRES_HOST_AUTH_METHOD=trust`; the bootstrap SQL also creates application login roles without passwords and the application DSNs omit credentials. This permits passwordless connections from the Compose network, so W8 cannot be called deployment-ready. The Compose bootstrap now requests SCRAM in both `POSTGRES_HOST_AUTH_METHOD` and `POSTGRES_INITDB_ARGS`, requires a superuser password for a new database, creates nine application/test roles with independent environment-backed passwords, and adds only the matching password to each service DSN. Blank credentials remain in `.env.example`, making a new bootstrap fail closed. `pnpm verify:w8:postgres-auth` passed against the pinned PostgreSQL image in a `network=none`, unpublished, disposable container: all nine roles accepted the correct random password and rejected both absent and wrong passwords. The container and mode-0600 temporary random credentials were removed after the check.

Existing data directories do not re-run init SQL or rewrite `pg_hba.conf`; prior volumes can still retain `trust` until a separately backed-up maintenance migration changes role passwords and host rules. This change has not been deployed or applied to any active DB/volume. W8 therefore remains blocked on existing-volume migration design/evidence, credential installation/rotation, paired backup and restore/RPO/RTO, and real Ubuntu validation. The evidence JSON records both the PASS for fresh bootstrap and the unresolved existing-volume blocker.
